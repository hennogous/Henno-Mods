## Verified engine boundary

The actual loaded native database from `csc-ai-fixed-research-visible-20261019/extended-250b/loaded-native-gameplay.sqlite` has no `ResourceModifiers` table. A table invented in SQL would not acquire engine behavior merely by using that name. Existing plot-modifier collections can filter exact resources, as CSC already does.

Native `Adjacency_YieldChanges` supports exact `AdjacentImprovement`, `AdjacentFeature`, `AdjacentTerrain` and `AdjacentDistrict`, plus `AdjacentResource` (a boolean), `AdjacentSeaResource` and `AdjacentResourceClass`. It has no exact ResourceType or arbitrary CSC TypeTags predicate. Resources have one native ResourceClassType; reclassifying Flax into an invented industry class would interfere with bonus/luxury/strategic semantics and cannot express its membership in several industries. `Resource_YieldChanges` is also not a Quarter-specific adjacency mechanism.

The relevant distinction is prospective native district valuation versus an effect applied after objects exist, not whether the SQL uses the Modifiers table. Some native modifier effects register real terrain/feature/improvement adjacency. CSC's current40/80 instead changes resource-plot yields. The original v1 conditional district material bonus was measured on completed districts but absent from prospective `Plot:GetAdjacencyYield`; actual material placement did not improve convincingly. Do not present another completed-yield check as proof of AI forecasting.

## Material placement: small discriminating tests first

First try an improvement-owned, resource-filtered bonus **received by an adjacent matching Quarter**, rather than the current bonus received by the improvement plot. An improved Flax resource exists before Quarter placement, so its modifier would already be present when the AI evaluates a future Tailors site. This ownership/receiver combination differs from v1's Quarter-owned completed bonus. Native player-district yield effects plus exact owner-resource and subject Quarter/distance filters are the proposed implementation route; resource-relative scope, actual application and forecasting all need separate native verification. Do not claim prospective recognition in advance.

Use a disposable city with two equally legal and affordable Quarter sites, one next to improved Flax and one next to an irrelevant resource. Hold the accepted baseline fixed, change only the new signal, mirror the physical sites and record actual AI selection. Compare prospective plot adjacency, completed district output and chosen site separately. Include a native adjacency positive control. No250turn run until there is a behavioral signal.

If that fails, an exact native-adjacency prototype can use one Flax-specific Farm improvement variant, with the normal Farm appearance/economy, and an `AdjacentImprovement` rule on Tailors. The cloned type is an addressable native predicate, not a dummy feature. Prototype it only in a disposable fixture. Production adoption would require inheriting Farm yield/tech/civic/modifier behavior, build rules, AI accessibility and compatibility; do not automatically replace Farms on real maps. It only represents improved materials and therefore does not solve initial placement beside unimproved deposits. This is a conditional, more invasive fallback, not an approved broad redesign. Existing generic bonus guidance can remain the initial raw-resource proxy. Future feature-based Quarters can use exact native feature adjacency directly.

## Research: test native unlock valuation, then bounded selection if needed

One cheap new preference-free test is an additional private **Tailors–Harbor native adjacency unlocked by Naval Tradition**. `Adjacency_YieldChanges` has PrereqCivic/PrereqTech columns, so this puts a benefit into an existing native unlock representation. The hypothesis is that research valuation may forecast it even though our conditional plot-yield Service modifiers were not forecast effectively. Native schema support does not prove this forecasting behavior. OFF/ON matched research-choice fixtures should establish actual choice changes before refinement or natural play. The first exaggerated signal is diagnostic and applies to all qualifying Tailors–Harbor adjacencies; it is not an exact material/Workshop/Lighthouse readiness rule and must not be silently deployed as one.

There is a stronger RH precedent than preference lists: installed RH5.097 `core/Strategies/Advanced_Thinking/Features/AutoPurchase/RH_AutoPurchase.lua:4223–4253` enables Sailing steering for suitable non-human coastal players. It checks research availability, calls `SetResearchingTech` and verifies the selected index, trying hash then index. Its update path calls `RH_RT.SailSteer` at5193. This is explicit research selection, not evidence that a preference weight was consumed. No source copying is needed.

A CSC fallback could select a missing Service civic/tech at a natural research-choice boundary, for AI players only, when a completed unpillaged Quarter, relevant improved materials, functioning source building and adjacent functioning customer make that unlock immediately useful. The analogous culture API is `GetCulture():SetProgressingCivic`; legal availability and setter/readback semantics must be native-tested independently of the tech API. Preserve existing progress and avoid repeatedly interrupting current research. Select at most one target, log the reason and actual choice, and stop intervening after unlock or loss of readiness. Do not grant progress, free civics, inspirations or buildings. This supplements strategic decision-making explicitly; it is not proof the native planner learned Services.

For longer-term opportunities, separately evaluate the source/customer prerequisite chain and native building/district incentives. The first bounded planner should handle only immediate opportunities, making its effect interpretable. Current material-supported natural Tailors lacked Lighthouse adjacency as well as Naval Tradition, so a material-only research gate is insufficient.

Primary supplemental research: [Infixo's Systems notes](https://github.com/Infixo/Civ6-Real-Strategy/wiki/Systems) describe differing field semantics across AI systems and report a Technologies Favored-flag bug. This is historical author testing, not proof of the exact2026 build. RH's continued use of preference rows and its explicit Sailing setter are separate kinds of evidence. Increasing numeric Values again would not establish which path the engine consumes.

Recommended order: freeze accepted baseline; perform the small material receiver test and civic-gated native adjacency choice test separately; only if native guidance still fails, evaluate the Flax improvement prototype and/or a tightly bounded research-selection module. No more long combined-treatment games before the mechanisms show a distinguishable behavioral effect.
