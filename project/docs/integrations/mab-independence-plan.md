# CSC adjacency independence: audit and release plan

_Source audit: 1 October 2026. Scope revised by Henno on 2 October 2026. The audit below records the pre-migration build. A first implementation now exists; see [CSC bundled adjacencies](csc-adjacencies.md) for current wiring, test evidence and remaining release checks._

## Decision and source snapshot

Ship CSC with its own **CSC-scoped adjacency engine** and remove the hard MAB dependency only after gameplay and presentation parity passes. The agreed scope is Bakers' and Tailors' implemented gameplay plus **all additions and fixes implemented in the MAB fork**, including features those Quarters do not yet use. Specific-Wonder matching will also live directly in the replacement, preserving that previously developed capability and retiring the patch-helper workflow. Keep Ruivo's work credited prominently and build on the proven ideas (declarative rules, plot counting, property-backed yield modifiers). Use dormant test rules to verify unused features. Future Quarter designs are stale/speculative and will be reviewed as each Quarter is developed; they do not supply requirements for this migration. Extend the engine when a reviewed requirement actually needs a new capability.

All required adjacency functionality must be self-contained in the CSC Steam package: table definitions, generated modifiers/requirements, source matching, gameplay refresh, UI previews, descriptions, overlay mappings and localization. Players must not need MAB, our fork, or a patch script. The specific-Wonder matcher is part of the shared replacement evaluator used by gameplay and UI.

## What CSC uses today

**Entrypoints and load order.** `Civ Supply Chains.civ6proj` declares MAB mod ID `eaffc7c2-21d2-47e5-a060-ae55780d1337` as a hard dependency. MAB creates `Ruivo_New_Adjacency` and its support tables at load order `-1`, then generates modifiers very late (`1919810`). CSC's `CSC_Q_ALL.sql` defines `CSC_QuarterMaterialAdjacencyConfig` at `95`; the live Bakers, Tailors and optional ModSupport SQL supply `TypeTags`; `CSC_Ruivo_AdjacencyProcessor.sql` at `3000` writes rules to MAB's tables. The oddly named `CSC_MAB_DB_RingFix` action at `9999999` actually loads notifications' `CSC_UI_DB_Dynamic.sql`; it is not an adjacency fix and needs a name cleanup during migration.

| CSC rule family | Current source and MAB behavior | First-release requirement |
|---|---|---|
| Quarter material inputs | Bakers and Tailors each declare BASE/SPEC `RESOURCE_CLASS` tags; processor emits `FROM_RINGS_TYPETAG_RESOURCE`, +1 Production per owned, visible tagged resource in ring 1. Optional resource mods add `TypeTags` before generation. | Preserve class membership, ownership, resource visibility and additive ModSupport. A resource carrying both classes should contribute to both distinct rules, as today. |
| Quarter sales | A district tagged `CLASS_CSC_<Q>_SALES` gives the Quarter +1 Gold; `CLASS_CSC_<Q>_GOODS_PROVIDER` gives +1 Production. The processor uses `FROM_RINGS_TYPETAG_DISTRICT`, `MustOwn=1`, ring 1. | Preserve district tag matching, ownership and unique-replacement propagation. |
| Customer return yields | Districts tagged `CLASS_CSC_<Q>_SALES_<YIELD>` receive +1 of that yield from an adjacent Quarter via `FROM_RINGS_CAO_DISTRICT`. The processor emits explicit rows for base and one-level unique replacement districts. Current live examples include Bakers Food/Culture and Tailors Production/Culture. | Preserve direction, yield, IDs for clear diagnostics, and one-level unique district expansion. |
| Bakers Wind Mill | `FROM_RINGS_CAO_TERRAIN_SETS`, `IsHills`, `MinRings=Rings=0`; +1 Production on the Quarter's own hill plot, attached through `BUILDING_CSC_BAKERS_WIND_MILL`. | Preserve ring-zero semantics and the building gate. |
| Bakers Water Mill | `FROM_RIVER_CROSSING`, +0.5 Production per river edge, attached through `BUILDING_CSC_BAKERS_WATER_MILL`. | Match actual river-edge count and MAB's integer rounding of the combined result. |
| Tailors river | `FROM_RIVER_CROSSING`, +0.5 Production per river edge on the Tailors' Quarter without a building gate. | Same river semantics and rounding. |

Every current processor row has `ProvideType='SelfBonus'`. No live CSC row requests MAB's other yield providers, multipliers, properties, storms, air slots, amenities, loyalty, tourism, etc. The generic `CSC_QuarterMaterialAdjacencyConfig` permits CAO-by-resource/feature/terrain types, but none of the currently active Bakers/Tailors config rows use them. Present usage alone must not narrow the implemented fork features below. Inherited MAB functionality is needed where it underpins current gameplay or those features; reproducing the entire unrelated MAB framework is not the migration objective. The other six Quarter actions are currently `DoNothing` stubs.

The gameplay boundary here is the adjacency dependency. Existing Bakers/Tailors effects delivered by CSC's own SQL, population-return, trade-route or Service systems must retain their behavior through the migration. Their engine requirements come from live implementation and approved contracts, not speculative future-Quarter prose.

**Engine behavior.** MAB counts plots in gameplay Lua, writes binary flags to the district plot, and SQL-generated `REQUIREMENT_PLOT_PROPERTY_MATCHES` modifiers convert those flags into actual district base yields. Its bit list is 1–512 (maximum encoded amount 1023). It refreshes on district build progress/completion and player turn activation; it does not currently register a comprehensive set of improvement/resource/ownership change events. CSC must retain actual yield behavior for human and AI players, save/load restoration, fractional river totals and ownership changes. Tooltip-only parity is insufficient.

**Presentation behavior.** MAB also supplies district adjacency descriptions, placement previews, tile-edge icons and a district detail panel. Our fork's placement work distinguishes CAO icons from source-type icons, avoids revealing undiscovered resources, respects `MustOwn`, handles all six river edges and their directions, and prevents duplicate river icons. Its UI imports a broad `UI/Common/AdjacencyBonusSupport.lua` override. CSC should show its own rule breakdown and previews with correct signs and icons while leaving unrelated districts' normal UI alone. Treat this as a separate deliverable, not as an incidental result of the gameplay Lua.

## Scope and coverage authority

Use two concrete inventories: generated rules from the current Bakers/Tailors build, and the complete fork diff against its upstream base `e978e6c`. Add the historical specific-Wonder matcher as the explicitly included CSC extension. Turn these into a coverage matrix of changed functions, schema fields, generation behavior, text and UI paths. Every addition/fix needs a reproduced behavior and a verification case, even when its test rule remains dormant. Do not treat the summary table above as permission to omit variants within a feature family.

Future Quarter prose is background only. Wonder era groups, new aggregation modes, technology-expiring feature bonuses and other speculative requirements have been removed from this migration plan. Review them when their actual content is developed. A later approved requirement should add a focused engine extension and regression coverage at that point.

## Implementation plan

1. **Freeze a parity fixture.** Export the actual generated CSC rules from a known-good MAB-backed runtime database, with IDs, district type, source type/tag, yield, amount, owner, ring bounds and building owner. Capture gameplay yield and UI screenshots on a compact map containing Bakers and Tailors, owned/unowned resource tiles, every relevant customer district, one unique replacement, hill/non-hill placement, zero to several river edges, and discovered/hidden resources. Save the MAB version and fork commit with the fixture. The SQL processor's output, not the historical manual, is the rule inventory authority.
2. **Define a CSC-only rule table and generator** under `Civ Supply Chains/Lua_UI/Adjacencies/` (or move SQL under `Data/` if that makes action ordering clearer). Keep `CSC_QuarterMaterialAdjacencyConfig` and the tag grammar as authoring inputs. Adapt the existing processor to emit `CSC_AdjacencyRules` with source type/key, district, yield, signed amount, owner filter, min/max ring and attachment information. The supported source registry and metadata must cover current rules, all source variants needed to reproduce the fork changes, and exact named-Wonder matching. Preserve the fork's unique-district clone fields and overlay mappings. Validate unsupported source types at build/test time rather than silently dropping them. Use `CSC_` names throughout, so MAB can coexist without duplicate evaluation.
3. **Generate only the needed yield modifiers.** Retain the proven bit/property mechanism initially: create CSC-namespaced bit requirements and `MODIFIER_PLAYER_DISTRICT_ADJUST_BASE_YIELD_CHANGE` actions for `SelfBonus`, attach district rows directly, and attach Wind/Water Mill rows through their building. Check the exact attachment collection and district targeting against the runtime database before finalizing SQL. Store integer yield amount after multiplying count by `YieldChange`, with the same truncation toward zero and cap as the current fork; on every recompute clear stale bits, including when the building disappears or the rule ceases to apply. Consider a smaller maximum only after proving the cap covers all realistic rule totals.
4. **Implement focused gameplay Lua.** Cache rule rows and tag membership; share an evaluator between runtime updates and preview calculations, with context-specific visibility supplied explicitly. Implement the source variants in the current-rule and fork-diff coverage inventories. Preserve their actual counting semantics, bounded ring enumeration, ring zero and map wrapping. Keep gameplay visibility and ownership explicit. Refresh at load, district completion, turn activation, and verified plot/resource/ownership/building events needed for prompt updates. Guard nil/incomplete districts and avoid a full-map scan on each event. Verify when the engine exposes city/district/building state before relying on it.
5. **Implement CSC-scoped presentation.** Reuse the evaluator in a UI-side module for placement numbers, district detail text and edge overlays. Port the behavioral fixes above: signed values, local/adjacent wording, hidden-resource filtering, ownership, river-edge direction/deduplication, CAO icon selection. Prototype the least invasive hook into Civ VI's existing adjacency support and document conflicts with MAB or other UI mods. Keep only CSC rule rows in the custom output. If a global support-file replacement is unavoidable, constrain its changes and test vanilla and popular UI mods explicitly.
6. **Switch the project wiring in one reviewable change.** Add CSC schema, generator, modifier SQL, gameplay Lua, UI import/context, localization and icon files in `project/modbuddy/CivSupplyChains.actions.json`, then regenerate/check `.civ6proj` with the project tool. Remove the MAB `<Dependency>` and old Ruivo table writes only after the new actions load and pass. Rename the misleading `CSC_MAB_DB_RingFix` action without altering its notification file. Search the built `.modinfo` and shipped files for remaining `Ruivo_`, `MAB`, and MAB ID references; retain only attribution and historical documentation. Update `AGENTS.md`, the CSC skill, project docs and public installation instructions after migration, so they no longer call MAB mandatory.
7. **Release gate.** Test CSC as the only enabled gameplay mod (plus XP1/XP2), then optional resource/customer mods, then MAB also enabled for coexistence. Compare each fixture's actual yields and visible previews against the saved baseline, including AI and human, city capture/ownership changes, resource discovery/removal, district construction, building construction/removal, reload, and a 50-turn autoplay. Check `Database.log`, `Modding.log`, runtime modifier/property rows and load times. Verify the Steam build has no MAB dependency and fresh subscribers can start a game without installing MAB. Treat an existing-save migration as separate: test explicitly, or state in the release notes that a new game is required.

The release gate also requires dormant rules covering all otherwise-unused fork additions: wider ring bands and boundaries/ring zero, ownership across affected source variants, negative amounts and truncation toward zero, signed text/icon selection, CAO and non-CAO overlays, resource visibility, river directions/deduplication, district tags and preservation of unique-district clone options. Add specific-Wonder cases for the named vs wrong Wonder, complete vs unfinished, owned vs foreign, and inside vs outside the inclusive ring bounds. Use the pinned fork and documented historical matcher as their respective behavioral references and check every row of the coverage matrix. Verify the fresh CSC package works without running `patch_mab.py` or installing MAB. Capability tests must not activate unfinished Quarter phases.

## Boundaries and decisions to revisit

- The first version preserves **live Bakers and Tailors** behavior, all implemented fork additions/fixes, and self-contained specific-Wonder matching. Future Quarter designs require review as those Quarters are developed; add new engine features only when reviewed requirements actually need them.
- The local fork and June PRs remain valuable upstream contributions. CSC's independence should not require withdrawing them; future upstream changes can still inform CSC fixes.
- Record Ruivo as the originator of MAB's architecture and adjacency work, with a link to the [upstream repository](https://github.com/revoltl/NEW_ADJACENCY_BONUS_BY_RUIVO) and Workshop item in CSC's source acknowledgments, public docs and Steam description. Document which implementation decisions were adapted and any licensed code if that changes.
- Do not claim full parity until the runtime fixture, gameplay verification and UI verification all pass. The current audit is source-based and cannot establish final in-game behavior.
