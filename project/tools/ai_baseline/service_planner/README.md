# Service-aware foundation planner v1

This is a separate next-version prototype, not a continuation of the closed
three-world study. It does not install gameplay, start Civ, create worlds, add

## Policy

Choose the useful Service first. Stage2/3 routes accept Base-only supply;
stage4 requires Base and Specialty at the same source. Within comparable plans,
Base count precedes Specialty count. Exact host buildings and research come from
`PROFILES`; agendas alone are not a strong observed demand signal.

Strong Service purchase: need >=0.8, need/chain confidence >=0.75, an existing
functioning customer, its Service civic already unlocked, and a credibly buildable
chain within20turns. The service
must still be relevant (Dockmaster naval-production premium ends after the
Renaissance). General good Quarter opportunities receive no Service premium.

Let available gold be current treasury less the largest of150gold, the driver's
emergency reserve, or10turns of current deficit. Strong plans may spend at most
25%of that balance, capped at200gold; general plans8%, capped at60gold. Spend in
the last5turns also consumes the allowance. At most2purchases/player/5turns,
one/city/10turns, and one outstanding purchase/player. These are transparent
starting values, not empirically calibrated gold-return estimates.

At600gold with a150reserve: strong allowance112gold, general36gold. An80gold
final tile can therefore be bought for a strong Dockmaster route and deferred
for an otherwise identical general Quarter opportunity. This implements the
human's request to be more forward for strongly aligned Services.

Only one final missing tile is acquired in v1. It may be the Quarter or a
required material tile; the rest of the actual chain must already be owned.
Contested/unrevealed plots, undiscovered materials, missing native legality,
unverified projected legality and imminent natural border acquisition do not
receive automatic purchases. A second Base offers a stronger ranking, but v1
does not change the AI's resource-harvest or improvement weights.

## Integration

Use `Coordinator` with the maintained `full_game_controller` instance as runner.
The driver supplies native observations through the adapter contract in
`coordinator.py`, with a fresh Core safe-boundary proof. Broad scans run every
5turns by default (configurable5–10); events only mark cities dirty. Cheap
refresh is mandatory every safe cycle. Unowned future targets belong in the
wide plan, not an immediate native build list. Source/customer/material facts
and resource visibility must refer to the specific candidate chain.

The current prototype provides the policy/coordinator/purchase bridge, **not a
new native world collector or mod event registration**. An existing driver must
bind its native snapshot and legality APIs to this adapter before a live test.
In particular, the vanilla documented grand-strategy getter does not enumerate
all active strategic plans. `needs.py` labels observed and inferred demand
explicitly; a verified native strategy adapter can supply stronger evidence.

Native `PARAM_PLOT_PURCHASE` is supplied by the driver after discovery; it is not
guessed or copied from a fixture. Spending is off by default. When enabled,
`native_purchase.lua` rechecks current city/plot ownership, AI identity,
same-type duplicates, supply/visibility, exact customer, projected district
legality, current price and treasury, reserve and native purchase permission.
It invokes **one** `CityManager.RequestCommand(..., PURCHASE, ...)`. It does not
use ownership setters or debit gold through a scripted substitute.

The journal is fsynced before dispatch. No acknowledgment, timeout or Lua error
allows automatic resending. A later fresh read must show actual tile ownership
AND the exact real treasury deduction before confirmation. Ambiguous changes
stay pending for manual/native investigation; no repeat mutation. Restarting
restores pending purchases, confirmed spend and cooldowns from that journal.

Foundation placement follows a later fresh owned-land check through the
driver's existing validated0%-production transaction. Purchase callbacks never
place a foundation. The coordinator accepts completion only with owner/plot/type,
zero-before/after, positive unchanged cost, incomplete native district and
unchanged queue proof. Durable attempted identities prevent automatic replay.
